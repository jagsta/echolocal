# Drop-In Intercom Probe — echod / go-esphome-device Sideband Audio Capability Audit

Resolves D-DI-7's protocol-level gate (specs/dropin-decisions.md:40) for D-DI-1..7. Audited 11 Oct 2026 against the source echod actually builds: `github.com/ygelfand/go-esphome-device v0.0.13` (go.mod:12) and its runtime library `github.com/ygelfand/libcountertop` (go.mod dependency of echod). go-esphome-device and libcountertop are external modules, not files in this repo; citations to them carry the repo-path inside the module. Everything else cites this repo.

TL;DR: **Continuous sideband audio CAN ride the existing ESPHome native API messages; HA CAN mediate it; the v1 relay (D-DI-4) needs NO go-esphome-device protocol extension.** The seam is the device-side turn model in `VoiceSatellite` (single subscriber, single open turn) — v1 holds one perpetual turn per device for the call's duration. The AEC is already userspace software inside echod's mic pipeline, fed by a hardware loopback reference channel, so the v2 open-duplex path is reachable too.

## 1. Audio primitives go-esphome-device implements

go-esphome-device ships the device half of the ESPHome native API (`go-esphome-device/api/api.pb.go`, generated from `go-esphome-device/proto/api.proto`). Audio-capable surfaces:

- **Voice assistant** — `go-esphome-device/voice.go`, type `VoiceSatellite`. Handled inbound: `SubscribeVoiceAssistantRequest` (`voice.go:227-243`; flags carry `VOICE_ASSISTANT_SUBSCRIBE_API_AUDIO`, `voice.go:232`), `VoiceAssistantResponse` (`voice.go:245-254`), `VoiceAssistantEventResponse` (`voice.go:256-271`), `VoiceAssistantAudio` → forwarded to `OnTTSAudio(data, end)` for playback (`voice.go:273-277`), `VoiceAssistantConfigurationRequest`/`VoiceAssistantSetConfiguration` (wake words, `voice.go:279-293`), `VoiceAssistantAnnounceRequest` (`voice.go:295-304`), `VoiceAssistantTimerEventResponse` (`voice.go:306-317`). Device-initiated outbound: `VoiceAssistantRequest{Start: true/false}` (`StartTurn`/`StopTurn`, `voice.go:155-190`), `VoiceAssistantAudio{Data}` (`SendAudio`, `voice.go:193-201`) and `VoiceAssistantAudio{End}` (`EndAudio`, `voice.go:204-212`).
- **Media player** — `go-esphome-device/domain_mediaplayer.go`: entity descriptor, state/volume/mute reporting, and `MediaPlayerCommandRequest` handling (`domain_mediaplayer.go:158-192`). Crucially `MediaPlayerCommandRequest` carries a **media URL**, not PCM — HA converts sources to WAV and serves them over HTTP (`libcountertop/pkg/media/mediaplayer/player.go:134-184`: `if c.HasMediaURL && c.MediaURL != "" { p.play(c.MediaURL, ...) }`, comment at :175 "Home Assistant serves the url as WAV"). So media_player is fetch-and-play, **not** a continuous PCM channel.
- **Voice feature flags** advertised to HA (`voice.go:18-34`): VoiceAssistant, Speaker, APIAudio, Timers, Announce, StartConversation, and a `FeatureMultiChannelAudio` bit (1<<6, "when a second mic source exists" — declared but the enum is transcribed from ESPHome C++; echod's advertised set is `libcountertop/pkg/assistant/satellite/satellite.go:15-19`, i.e. DefaultVoiceFeatures|Speaker|Announce|StartConversation|Timers — MultiChannelAudio is NOT advertised).
- Nothing else carries audio: camera (`domain_camera.go`) is image frames; bluetooth (`domain_bluetooth.go`), light/switch/sensor/update/event are control-plane only. Grepping `api.pb.go` for `Audio` yields only the VoiceAssistant* family.

So the only PCM frame channel on the wire is `VoiceAssistantAudio`, in both directions, outside any turn when unsolicited.

## 2. Can echod open a second concurrent stream while the voice assistant is registered?

**Microphone (mic out): yes, already supported.** echod's ALSA capture is a single shared `mic.Source` fan-out (`internal/hardware/mic/mic.go:153-352`, `Run` loop broadcasting to named listeners). `Source.Listen(name)` registers any number of concurrent listeners (`mic.go:236-264`); frames are offered non-blocking with per-listener drop accounting (`mic.go:459-468`). Precedent: the existing call feature already runs a second consumer alongside the wake/turn listener — `internal/feature/call/sound.go:15` `mic.Get().Listen("call")`, and the assistant turn takes its own `Listen("turn")` (`libcountertop/pkg/assistant/turn/conversation.go:706`). A third "intercom" listener is additive, not a new capture device.

**Speaker (speaker in): yes, via the output mixer's stream bus.** echod's playback pushes named stream types onto one ALSA writer (`internal/hardware/speaker/speaker.go:396-403`, `PlayStream(s config.Stream, samples)` → `p.bus.Push(s, samples)`). The stream enum is the five fixed types Main/Media/Alerts/Voice/Feedback (`internal/config/volume.go:10-18`). Adding a sideband call stream means one new `Stream` value plus a level entry in the two switch tables in `volume.go` — mechanical, no architectural change. The existing webrtc-based `call` feature (`internal/feature/call/call.go:30-56`, `libcountertop/pkg/media/call/call.go`) already proves mic-listener + playback mixing can run concurrently with HA voice.

**The real constraint is the protocol handler, not the audio pipeline.** `VoiceSatellite` supports exactly one subscriber connection and one open turn: `v.conn` is a single field (`voice.go:131-134`), `SubscribeVoiceAssistantRequest` overwrites it (`voice.go:230-236`), and `turnOpen` is a single bool — a second `StartTurn` while one runs returns `ErrTurnInProgress` (`voice.go:162-167`); `Run` end/error events clear it (`voice.go:262-267`). A wake-word turn during an active sideband stream would be refused by the library, and conversely the sideband stream *is* a turn — which conveniently matches D-DI-5's "wake word suppressed on both ends during active calls" (though the suppression then happens as a resource conflict, not policy; see §4 for the policy hook).

## 3. Gen 2 hardware AEC / noise path — reachable from echod?

**Reachable, and in fact already exercised by echod — but it is software AEC fed by a hardware reference, not an on-chip AEC datapath.** The Dot's capture stream interleaves microphone channels **plus loopback reference channels**: "The loopback is the DAC feed, bit exact, decimated and aligned with the microphones by the same hardware" (`mic.go:289-290`), `Refs = Channels - Mics` (`mic.go:35`). echod runs a userspace canceller over them: `Source.cancel *aec.Canceller` (`mic.go:67`), built at `mic.go:114`, applied per-frame against the loopback reference in `broadcast` (`mic.go:384-403`, `cancelCenter` at `internal/hardware/mic/cancel.go:45-58`), with a noise/echo suppressor preprocessor in front (`cancel.go:12-23`, `mic.go:121`). It is user-toggleable (`SetCancelling`, `cancel.go:107-111`) and already wire-attached to the `microphone_cancel_echo` setting (`internal/feature/microphone/microphone.go:~68-80`).

For the intercom: this is exactly the path a sideband stream needs — the callee's own playback (the far end's voice) flows through the DAC, the hardware loopback hands the canceller its reference, and `Playing() bool` tracking (`mic.go:60-81`, `s.SetPlayback` at `mic.go:379`) already exists for hold/freeze logic. **Verdict: no new kernel/DSP work needed for open duplex; it rides the existing canceller.** Caveat for v2: adaptation must be driven while the intercom stream plays (same as media: `SetAdapting`/`Freeze` hooks, `cancel.go:113-121`), and double-talk behavior is whatever `libcountertop/pkg/audio/aec` delivers — measure ERLE (`cancel.go:100-105`) on the pilot before promising parity with Amazon's far-field AEC.

## 4. Recommendation: does HA-relayed v1 (D-DI-4) need a protocol extension?

**No. Name of the seam: the device-side turn model in `VoiceSatellite` — hold one perpetual per-call turn per endpoint, and relay `VoiceAssistantAudio` frames through HA.** Nothing on the wire limits `VoiceAssistantAudio` to short captures; `End` is an explicit optional marker (`voice.go:204-212`, `api.proto:2041`), and mic frames flow device→HA whenever the app sends them (`SendAudio` is device-initiated, `voice.go:90-93` — "The device initiates every turn, so nothing here is driven by Home Assistant polling").

Concrete v1 shape (per D-DI-4: "both Dots use their existing ESPHome native API connections; a HA-side component relays PCM and owns call state"):

1. Caller dials; HA custom component (call-state owner) sends, over each device's existing native API connection, the existing messages: on the caller, ` VoiceAssistantRequest{Start:true}` equivalents flow device-side — the caller's echod calls `StartTurn("intercom", ...)` once (`voice.go:155-177`), then `SendAudio(frame)` continuously from a new mic listener, `EndAudio()` at hang-up. On the callee, HA plays the ring chime via media_player URL (existing path, §1) and on accept likewise opens the callee's perpetual turn.
2. HA component relays each side's `VoiceAssistantAudio.Data` to the peer as `VoiceAssistantAudio` (the TTS playback direction each device already handles at `voice.go:273-277` → through echod's `speaker.PlayStream`). Note each device maintains its own native API connection to HA — no connection sharing needed.
3. Signalling (ring/accept/hang-up/busy/mute) is ordinary entity/commands traffic (buttons, sensors, services) — D-DI-3/5/6 machinery needs no audio protocol work at all. The 3-second ring floor lives in the HA session state machine (D-DI-7 convention).

Costs/limits to record in the session-layer cards:
- **The call occupies the device's only turn.** While the sideband turn is open, wake-word turns are refused (`ErrTurnInProgress`, `voice.go:162-167`) — matches D-DI-5's suppression requirement, but "suppress" must be implemented deliberately (e.g. intercept the wake path before `StartTurn`) rather than left to the error.
- **HA is in the audio path frame-by-frame** — accepted v1 consequence (call drops on HA restart, D-DI-4); relaying 16 kHz PCM through HA's assist satellite connections is within what HA already does for every Assist turn.
- **One subscriber per device.** `v.conn` holds a single voice subscriber (`voice.go:131-142`); if HA ever opens a second subscription it silently steals it (`voice.go:230-236`). Fine for v1.
- **echod-side additions (this repo, not go-esphome-device):** a new mic listener name, a new `config.Stream` value for call playback with volume mapping (`internal/config/volume.go`), and a tiny `Feature/intercom` binding the session state machine to `StartTurn`/`SendAudio`/`EndAudio` and `speaker.Get().PlayStream` — the same wiring pattern `internal/feature/call/` already uses.
- **v2 P2P (direct echod↔echod LAN) is where the go-esphome-device extension actually lands** — consistent with D-DI-4:21 ("protocol extension lands in go-esphome-device at that point"): new custom message + handler in the `Chain` (handler seam at `go-esphome-device/entities.go:248` / `libcountertop/pkg/homeassistant/nativeapi/server.go:116`), bypassing HA entirely for data while keeping the same session services.

Bottom line for the blocking cards: **D-DI-4's HA-relayed v1 is buildable entirely on existing messages; the seam is one perpetual turn per device + HA-side frame relay. Reserve go-esphome-device protocol work for v2 P2P.**
